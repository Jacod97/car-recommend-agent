# 저장소 구조

작성일: 2026-11-24 · 기준: 같은 날 고친 `docs/project.md`와 `docs/agent-design.md`, `listing_analysis.ipynb`

## 1. 구분 기준

저장소의 Code는 System과 일회성 Code로 나눈다. System은 Agent, 도구, 이 둘을 묶는 Pipeline, 데이터 전처리로 이루어진다. Agent는 LLM(Large Language Model)을 호출하는 단계 6개이고, 도구는 LLM 없이 Code로 계산하는 단계 2개다. Pipeline은 Agent와 도구를 정해진 순서로 호출하는 Code다. 일회성 Code는 데이터를 모으거나 살펴볼 때 사람이 직접 실행하는 Code이고, System은 이것을 import하지 않는다.

두 쪽은 `data/processed/`의 파일로만 이어진다. 수집 Script가 이 경로에 출처별 `.jsonl` 파일을 쓰고, System의 전처리가 그 파일을 읽는다.

최상위 경로는 표 1과 같다. 작성일 기준 `src/`는 아직 없고, 나머지 경로는 지금 위치 그대로다.

표 1. 최상위 경로

| 경로 | 구분 | 내용 | Git |
|---|---|---|---|
| `src/` | System | Agent, 도구, Pipeline, 전처리 | 포함 |
| `scripts/` | 일회성 | 수집 Script 5개 (`crawl*.py`) | 포함 |
| `listing_analysis.ipynb`, `review_analysis.ipynb` | 일회성 | 수집한 데이터를 분석한 Notebook | 포함 |
| `data/` | 데이터 | 수집 결과(`raw/`, `processed/`)와 전처리 결과 | 제외 |
| `docs/` | 문서 | 설계 문서 | 포함 |
| `pyproject.toml`, `uv.lock` | 설정 | 의존성 | 포함 |

## 2. src 구조

`src/`에는 Package 하나를 두고, 그 안을 네 묶음과 공통 파일 네 개로 나눈다. 그림 1이 전체 구조다. 파일 오른쪽에는 그 파일이 하는 일을 적었고, `agents/`와 `tools/`는 `agent-design.md`의 이름을 앞에 붙였다. 파일마다의 설명은 3장부터 7장에 있다. SQL은 Structured Query Language, DB는 Database를 줄인 말이다.

그림 1. src 구조

```text
src/carrec/
├─ agents/
│   ├─ orchestrator.py             오케스트레이터: 사용자와 대화, 담당 Agent 정하기
│   ├─ consult/                    상담: 사용자를 상대하는 쪽
│   │   ├─ needs_analysis.py       니즈 분석: 대화를 니즈로 정리
│   │   └─ dealer.py               딜러: 5대 고르고 이유 설명
│   └─ search/                     탐색: 차와 근거를 찾는 쪽
│       ├─ model_selection.py      모델 선정: 후보 모델 고르기
│       ├─ sql_agent.py            SQL 에이전트: SQL을 써서 DB 조회
│       └─ review.py               리뷰: 모델에 대한 근거 찾기
├─ tools/
│   ├─ finance.py                  재무: 감당 가능한 예산 계산
│   └─ scoring.py                  점수 계산: 매물 순위 매기기
├─ pipelines/
│   ├─ turn.py                     사용자 입력 한 건 처리
│   └─ recommend.py                추천: 니즈 분석에서 TOP5까지
├─ preprocess/
│   ├─ normalize.py                출처별 매물을 한 형식으로 통합
│   ├─ car_models.py               모델명 통일, 차종 · 제원 정리
│   ├─ fair_price.py               매물별 적정가 계산
│   ├─ review_index.py             리뷰 벡터 인덱스 생성
│   └─ build.py                    전처리 전체 실행
├─ schemas.py                      공용 데이터 형식
├─ session.py                      대화 상태 저장
├─ llm.py                          LLM 호출
└─ config.py                       경로와 상수
```

네 묶음의 역할은 표 2와 같다.

표 2. 묶음의 역할

| 경로 | 역할 | 실행 시점 |
|---|---|---|
| `agents/` | LLM을 호출하는 단계. 파일 하나에 Agent 하나. 오케스트레이터 아래를 `consult/`와 `search/`로 나눔 | 사용자 요청마다 |
| `tools/` | LLM 없이 Code로 계산하는 단계. 같은 입력이면 항상 같은 결과가 나옴 | 사용자 요청마다 |
| `pipelines/` | Agent와 도구를 정해진 순서로 호출함 | 사용자 요청마다 |
| `preprocess/` | 수집 결과(`data/processed/`)를 System이 읽는 데이터로 바꿈 | 수집 후 따로 |

### 호출 방향

- `pipelines/`는 `agents/`와 `tools/`를 호출함. 반대 방향 호출은 없음
- `agents/`와 `tools/`는 서로 import하지 않음. Agent 파일끼리도 import하지 않음. 순서와 전달은 `pipelines/`가 맡음
- LLM은 `agents/`만 쓰고, `llm.py`를 거쳐서만 호출함
- SQL은 `agents/search/sql_agent.py`에서만 실행함. 읽기 전용이며 SELECT만 허용함
- `preprocess/`는 다른 세 묶음을 import하지 않음
- `src/`는 `scripts/`와 Notebook을 import하지 않음

### 미정 사항

- Package 이름: `carrec`은 임시 이름
- `project.md`의 "화면"에 해당하는 Code의 위치. 화면은 `pipelines/turn.py`를 호출하고, "필터"는 LLM 없이 매물 DB를 바로 조회함

## 3. agents

Agent는 LLM을 호출해 입력을 정해진 형식의 출력으로 바꾸는 단계 하나다. `agent-design.md`의 "에이전트" 표에 있는 6개를 파일 하나씩으로 옮긴다.

`orchestrator.py`는 사용자와 직접 대화하는 하나뿐인 Agent라 `agents/` 바로 아래에 둔다. 나머지 5개는 무엇을 상대하는지로 나눈다. `consult/`(상담)는 사용자의 말을 이해하고 결과를 사용자에게 설명하는 쪽이고, `search/`(탐색)는 차와 근거를 찾는 쪽이다.

Agent 설명에는 `agent-design.md`의 용어를 그대로 쓴다. 뜻은 표 3과 같다.

표 3. Agent 설명에 쓰는 용어

| 용어 | 뜻 | 예 |
|---|---|---|
| 매물 | 판매처에 올라온 차 한 대 | |
| 모델 | 차 이름 단위의 구분. 한 모델에 매물이 여러 대 있음 | 쏘렌토, 그랜저 |
| 니즈 | 대화에서 뽑은 사용자의 요구. 아래 세 종류로 나뉨 | |
| 필수 조건 | 매물을 거르는 조건. 맞지 않는 매물은 결과에서 빠짐 | 디젤 제외, 사고차 제외 |
| 모델 수준 니즈 | 후보 모델을 고르는 기준. 같은 모델이면 매물마다 같아서 순위에는 쓰지 않음 | 승차감, 실내 공간, 디자인 |
| 매물 수준 니즈 | 매물의 순위를 매기는 기준. 항목, 목표, 중요도로 이루어짐 | 가격 2,500만원 근처, 주행거리 적을수록, 무사고 |
| 후보 모델 | 모델 수준 니즈에 맞아 조회 대상으로 삼는 모델 | 카니발, 쏘렌토, 싼타페, 스포티지 |
| 거절한 매물 | 추천받았지만 사용자가 마음에 들어 하지 않은 매물. 다음 추천에서 빠짐 | |
| TOP5 | 사용자에게 보여주는 추천 매물 5대 | |

파일마다 하는 일은 표 4와 같다. 예는 `agent-design.md`의 시나리오에서 가져왔고, 숫자는 그 문서가 밝힌 대로 설명용 예시다.

표 4. agents의 파일

| 파일 | 하는 일 | 입력 → 출력 | 예 |
|---|---|---|---|
| `orchestrator.py` (오케스트레이터) | 사용자와 직접 대화함. 추천에 필요한데 아직 모르는 정보를 한 번에 하나씩 묻고, 추천에 대한 반응이나 매물·모델 질문이면 담당 Agent를 정함. 담당 Agent가 낸 결과와 재무 계산 결과를 사용자에게 전함 | 사용자 입력 → 다음 질문 또는 담당 Agent | "예산은 어느 정도 생각하세요?"라고 물음. "2번 차 사고 이력 괜찮아?" → SQL 에이전트. "쏘렌토 하이브리드 실연비 어때?" → 리뷰 |
| `consult/needs_analysis.py` (니즈 분석) | 지금까지의 대화 전체를 읽고 니즈 세 종류로 정리함. 사용자가 추천을 거절하면 기존 니즈를 고치지 않고 대화 전체로 처음부터 새로 만들고, 거절한 매물도 함께 뽑음 | 대화 → 필수 조건, 모델 수준 니즈, 매물 수준 니즈, 거절한 매물 | "아이 둘이랑 주말에 장거리" → 모델 수준 니즈 "넓은 2열, 장거리 편안함", 매물 수준 니즈 "가격 2,500만원 근처, 연비 좋을수록, 무사고". "다 너무 커. 주차가 힘들 것 같아" → 모델 수준 니즈 "중형 이하, 2열 공간은 유지" |
| `consult/dealer.py` (딜러) | 상위 30대에서 5대를 골라 추천 이유와 함께 보여줌. 같은 모델은 많아야 2대 | 상위 30대 + 니즈 → TOP5 + 설명 | 모델을 섞은 TOP5와 매물마다의 추천 이유 |
| `search/model_selection.py` (모델 선정) | 모델 수준 니즈에 맞는 후보 모델을 고름. 모델의 제원은 `sql_agent.py`가 조회한 결과를, 근거는 `review.py`가 찾은 내용을 참고하며, 전달은 `pipelines/`가 맡음 | 모델 수준 니즈 → 후보 모델 | "넓은 2열, 장거리 편안함" → 카니발, 쏘렌토, 싼타페, 스포티지 |
| `search/sql_agent.py` (SQL 에이전트) | LLM에게 매물 DB와 제원 DB의 표·열 설명을 주고 요청에 맞는 SQL을 쓰게 한 뒤, 그 SQL을 실행해 결과를 돌려줌. 추천에서는 필수 조건과 후보 모델에 맞는 매물을 가져오고, 질문에서는 매물의 사고 이력이나 적정가 같은 내용을 가져옴. 만든 SQL은 대화 상태에 저장하고, 니즈가 바뀌지 않으면 다시 씀 | 니즈 또는 질문 → 조회 결과 (추천에서는 매물 수백 대) | 필수 조건 "디젤 제외, 사고차 제외"와 후보 모델 4개에 맞는 매물. "2번 차 사고 이력 괜찮아?" → 성능점검 단순교환 무사고, 보험 사고 1건(범퍼 47만원), 정보 없는 기간 있음 |
| `search/review.py` (리뷰) | 모델 하나에 대해 리뷰·커뮤니티 글에서 근거를 찾아 요약하고 출처를 붙임. 글은 리뷰 벡터 인덱스와 웹에서 찾음 | 모델 + 주제 → 근거 요약, 출처 | 쏘렌토 하이브리드, 연비 → 근거 요약 + 출처(보배드림, 유튜브, 시승기) |

### 특이사항

- `search/sql_agent.py`: SQL을 실행하는 함수를 이 파일 안에 둠. DB의 표와 열 설명, SELECT 검사처럼 파일이 늘면 `search/sql_agent/`로 바꿈
- `search/review.py`: 리뷰 벡터 인덱스를 검색하는 함수를 이 파일 안에 둠

## 4. tools

도구는 LLM 없이 Code로 계산하는 단계다. 같은 입력이면 항상 같은 결과가 나온다. `agent-design.md`의 "도구" 표에 있는 2개를 파일 하나씩으로 옮긴다. 파일마다 하는 일은 표 5와 같다.

표 5. tools의 파일

| 파일 | 하는 일 | 입력 → 출력 | 예 |
|---|---|---|---|
| `finance.py` (재무) | 사용자의 소득과 지출로 감당할 수 있는 차값을 계산함. 실수령, 한도, 할부, 유지비를 계산하고, 할부와 유지비가 월 여유를 넘으면 예산이 무리라는 결과와 감당 가능한 차값을 돌려줌 | 재무 정보(소득, 고정 지출, 희망 예산) → 예산 상한, 월 한도 | 연봉 4천만원, 예산 2,500만원 → 감당 가능, 월 한도 60만원. 월 여유 70만원, 예산 3천만원 → 무리, 감당 가능 차값 약 1,200만원 |
| `scoring.py` (점수 계산) | SQL 에이전트가 가져온 매물을 매물 수준 니즈에 가까운 순으로 줄 세워 상위 30대를 남김 | 매물 + 니즈 → 상위 30대 | "가격 2,500만원 근처, 연비 좋을수록, 무사고"에 가까운 순 |

### 미정 사항

`agent-design.md`의 "정할 것"에 있는 항목이다.

- `scoring.py`: 매물 수준 니즈의 목표에 가까운 정도를 계산하는 방법
- `scoring.py`: 딜러에 넘길 상위 매물 수 (30대 제안)
- `finance.py`: 월 여유 중 차량비로 쓸 수 있는 비율

## 5. pipelines

Pipeline은 Agent와 도구를 정해진 순서로 호출한다. `agent-design.md`의 흐름은 추천, 피드백, 질문 세 개인데, 여러 단계를 순서대로 묶는 것은 추천뿐이라 파일은 두 개다. 피드백은 거절한 매물을 빼고 추천을 다시 실행하는 것이고, 질문은 Agent 하나를 호출하는 것이라 `turn.py`가 맡는다. 파일마다 하는 일은 표 6과 같다.

표 6. pipelines의 파일

| 파일 | 하는 일 | 입력 → 출력 | 예 |
|---|---|---|---|
| `turn.py` | 사용자 입력 한 건을 받아 `orchestrator.py`를 호출함. 오케스트레이터가 다음 질문을 내면 그대로 답함. 추천이나 재추천이면 `recommend.py`를 실행함. 매물 질문이면 `sql_agent.py`를, 모델 질문이면 `review.py`를 호출하고, 그 결과를 오케스트레이터가 사용자에게 전함. 화면이 호출하는 진입점 | 사용자 입력 + 대화 상태 → 답변 | 시나리오 4 (특정 매물 질문), 시나리오 5 (모델 질문), 시나리오 6 (살 차 기준이 정해진 사용자) |
| `recommend.py` (추천, 피드백) | 오케스트레이터가 모은 대화로 TOP5를 만듦. 순서는 니즈 분석 → 재무 → 모델 선정(SQL 에이전트의 제원 조회와 리뷰 참고) → SQL 에이전트(매물 조회) → 점수 계산 → 딜러. 재무의 결과가 예산 무리이면 딜러까지 가지 않고 오케스트레이터가 사용자에게 선택을 물음. 재추천일 때는 거절한 매물을 결과에서 뺌 | 대화 → TOP5 + 추천 이유 | 시나리오 1 (뭘 살지 모르는 사용자의 첫 대화), 시나리오 2 (마음에 안 들 때), 시나리오 3 (예산이 무리일 때) |

## 6. preprocess

전처리는 수집 결과를 System이 읽는 데이터로 바꾼다. 사용자 요청을 처리할 때가 아니라 수집 후에 따로 실행한다. 만드는 데이터는 `project.md`의 "데이터" 상자에 있는 "매물 DB (통합)", "제원 DB", "리뷰 벡터 인덱스"다. 파일마다 하는 일은 표 7과 같다.

표 7. preprocess의 파일

| 파일 | 하는 일 | 입력 → 출력 | 예 |
|---|---|---|---|
| `normalize.py` | 출처마다 다른 항목 이름, 단위, 값의 표기를 한 형식으로 맞춰 매물을 한 표로 합침. 사고 여부의 기준도 하나로 맞춤. `listing_analysis.ipynb` 1절의 함수 `hyundai`, `kia`, `heydealer`가 하는 일을 맡음 | `data/processed/`의 출처별 매물 → 매물 DB (통합) | 가격: 현대는 문자열 "2,490만원", 기아는 원 단위, 헤이딜러는 만원 단위 → 만원 단위 |
| `car_models.py` | 출처마다 다른 모델명을 하나로 맞추고, 모델마다 차종과 제원을 정리함 | 출처별 매물, 표시연비 데이터 → 제원 DB | 헤이딜러의 "디 올 뉴 그랜저 하이브리드(GN7)"와 현대·기아의 "그랜저"를 같은 모델로 묶음 |
| `fair_price.py` | 매물마다 비슷한 차와 비교한 적정가를 계산해 매물 DB에 더함. `sql_agent.py`가 조회함 | 매물 DB → 매물별 적정가 | |
| `review_index.py` | 리뷰·커뮤니티 글을 `agents/search/review.py`가 검색할 수 있는 형태로 만듦 | `data/processed/`의 리뷰·커뮤니티 글 → 리뷰 벡터 인덱스 | |
| `build.py` | 위 네 파일을 순서대로 실행함 | | |

### 특이사항

- 작성일 기준 리뷰·커뮤니티 글을 모으는 수집 Script는 `scripts/crawl_bobaedream.py` 하나임
- `sql_agent.py`가 쓰는 SQL은 이 묶음이 만든 표를 조회함. 값의 표기와 모델명이 `normalize.py`와 `car_models.py`에서 통일되어 있어야 조건이 맞게 걸림

### 미정 사항

- `normalize.py`: 출처마다 다른 사고 여부를 하나로 맞추는 기준
- `fair_price.py`: 적정가를 계산하는 방법
- 전처리 결과의 저장 형식과 `data/` 아래 경로

## 7. 공통 파일

네 묶음이 함께 쓰는 파일이다. 표 8과 같다.

표 8. 공통 파일

| 파일 | 하는 일 | 쓰는 곳 |
